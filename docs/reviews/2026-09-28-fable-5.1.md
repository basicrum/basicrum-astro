## Assessment

The package follows standard Astro integration conventions: a typed ESM export,
an `astro:config:setup` hook, classic head-script injection, and a prerendered
endpoint for the self-hosted Boomerang asset. Both loader choices are supported.

The intended loader contract is explicit:

- `loader: "standard"` starts monitoring immediately and requires no consent
  callback. This behavior is correct and must be preserved.
- `loader: "consent"` waits for the site's external consent decision.

The duplicate-registration finding below concerns conflicting configurations of
both modes on the same site. It is not a finding against consent-free operation
of the standard loader, and its proposed validation adds no consent requirement
to that mode.

Two actionable P2 findings remain. The other recommendations concern test
coverage, documentation, or maintenance rather than demonstrated failures in the
current package. The documented absence of SPA route measurement is an existing
limitation, not a new review finding.

## P2: reject duplicate registrations

Location: `src/index.js:22` (integration setup).

A shared Astro preset can register the standard loader while the consuming site
adds another registration with the consent loader. The integration currently
accepts both. Each registration injects a bootstrap, but the first bootstrap sets
the browser singleton flag and the second returns immediately.

Codex built an Astro site containing, in this order:

```js
integrations: [
  basicrum({ ...options, loader: "standard" }),
  basicrum({ ...options, loader: "consent" }),
]
```

The output contained two bootstraps. Chromium sent a beacon before any consent
grant, and `typeof window.OPT_IN_BASICRUM_LOADER_WRAPPER` was `"undefined"`.
With two conflicting registrations, the effective loader mode therefore depends
on registration order. Immediate collection is expected and correct when the
standard loader is the site's selected mode.

Agreed recommendation: detect multiple `@basicrum/astro` integrations during
configuration and throw an actionable error. A warning would still allow the
ambiguous deployment. Keep the runtime singleton guard for script re-execution;
it is not a substitute for validating configuration.

Add coverage for both mixed-mode orders and repeated same-mode registrations.

## P2: preserve short visits when a beacon delay is configured

Location: `src/bootstrap.js:56` (`WaitAfterOnload.is_complete`).

With a positive `waitAfterOnloadMs`, the plugin reports incomplete until its timer
fires. This blocks all beacons, including the final unload beacon, during the
delay. A visitor who leaves shortly after load can produce no measurement.
The default delay is zero, so this finding affects the optional delay feature.
The WordPress plugin has the same boolean gate; this behavior is inherited.

Codex tested the actual vendored Boomerang bundle with a real localhost HTTP
collector and navigation about 500 ms after load:

| Scenario | Before navigation | Total after navigation | Beacon types received |
| --- | ---: | ---: | --- |
| Delay 0, current source | 1 | 2 | Page load, unload |
| Delay 5000 ms, current source | 0 | 0 | None |
| Delay 5000 ms, in-memory `rt.quit` exemption | 0 | 1 | Unload only |
| Delay 5000 ms, in-memory flush before RT unload | 0 | 2 | Page load, unload |

The candidate changes were applied only to generated JavaScript in the test
harness, not to the integration source.

Fable traced the bundle's unload path: plugin subscriptions run as `pagehide`
handlers, RT adds `rt.quit` with an empty-string value, and the core synchronously
calls `real_sendBeacon()` after the unload subscribers have run. The completeness
check receives the beacon variables. Presence of `rt.quit` matters; a truthiness
check would miss its empty-string value.

An `rt.quit` exemption alone preserves one request, but Boomerang classifies that
request as an unload beacon when `rt.abld` is absent. The collector's treatment of
that combination has not been checked.

Agreed recommendation: while the initial beacon is still pending, flush it during
`page_unload` before RT adds its unload fields. The current bundle initializes the
custom plugin before RT, which permits that ordering. Guard the flush with the
consent configuration and completion state, and clear the outstanding timer on
unload so a later BFCache restoration cannot trigger a stale delayed send.
Revalidate the ordering when upgrading Boomerang.

The in-memory prototype produced the expected page-load and unload event shapes;
this is not a claim of byte-for-byte payload equality or a completed production
fix. Add regression tests for early exit, late consent, withdrawal before exit,
and timer/BFCache behavior before applying the change. In particular, a grant
followed by withdrawal and navigation must not send a new beacon.

Validation lesson: the initial page-level Playwright request interception missed
unload traffic, including in the zero-delay control. Fable identified that issue,
and the real HTTP collector confirmed the expected control and candidate results.
Use server-side request capture for the unload regression test.

## Secondary recommendations

1. Strengthen the delay test at `tests/browser/integration.spec.js:121`. Assert
   that no beacon arrives before the configured delay, as well as eventual
   delivery. The current test checks only eventual delivery and a completion flag.
   Add a standard-loader case covering initialization before window load.
2. Automate a packed-package installation check as a release/CI gate. Codex's
   manual check passed: `npm pack`, install the tarball and Astro 7.3.5 into a
   separate consumer, import `@basicrum/astro` in its config, and build with a
   non-root base. The consent bootstrap and Boomerang asset were emitted correctly.
   Existing source-based SSR tests pass too; a packed SSR consumer and a served
   asset checksum would extend the release check.
3. Consolidate the duplicated Boomerang version references when changing the
   vendored build. All current references and provenance checks agree.
4. Remove the literal function-name coupling in `configure.toString()` if the
   integration source will be transformed or minified. No failure was observed in
   the current source, CLI build, or packed consumer.
5. Clarify Astro 7's built-in CSP handling in the README. Keep host cache guidance
   for `/_basicrum/` rather than moving into Astro's asset directory without adapter
   testing.
6. Add browser coverage for fallback `p_type`, more base-path variants, and avoid
   fixed-port conflicts if multiple test jobs share a host.

`repository` and `publishConfig.access` are optional npm metadata, not missing
runtime requirements. A public scoped release can also use `npm publish --access
public`.
