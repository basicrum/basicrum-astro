## Runtime and naming verdict

The rename covers the shipped core, adapter-facing declarations, bootstrap,
loader asset selection, fixtures, examples and packed-consumer check. The
beacon field names `brum_site_id` and `beacon_url` remain unchanged. Vendored
loaders and Boomerang remain unchanged. Browser assertions were preserved;
new unit and type assertions reject the former public names.

Keep the user-requested API:

```js
basicrum({
  brumSiteId: "YOUR_BASICRUM_SITE_ID",
  beaconEndpoint: "https://YOUR_COLLECTOR/beacon/catcher",
  loader: "non-consent",
});
```

The non-consent loader intentionally loads immediately without waiting for
a consent decision. The consent loader waits for the site's consent
manager. No new consent gate or legal claim is proposed.

The original review recommended `@basicrum/astro` because the scope already
identified the brand. This recommendation was superseded on 2026-10-13:
the owner chose `@basicrum/basicrum-astro` to follow the Basicrum platform
package naming pattern. The GitHub repository remains `basicrum/basicrum-astro`.

## First-release preparation

These are pending release tasks, not defects in the current unpublished
state:

1. Finalize the version and changelog together. The version check reads the
   first versioned heading and does not require Unreleased to be empty.
   Ensure the entry for the chosen first published version describes the
   new API; do not simply tag the current worktree and leave that decision
   implicit.
2. Prepare the npm installation instructions and publication wording in
   README as part of the release change. Keep local-install migration notes
   while they still help existing local users.
3. Confirm the publishing account has rights to the `@basicrum` npm scope.
   The current unattended workflow needs a short-lived granular token with
   package/scope publishing permission and bypass 2FA, stored as the
   `NPM_TOKEN` Actions secret. See the official
   [scoped publishing guide](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/).
4. Follow the repository's tag-driven release procedure after verification.
   First publication and its provenance still require validation in the real
   workflow. No manual or throwaway publication was performed for this audit.

## Trusted Publishing migration

Once the package exists, configure GitHub Trusted Publishing for owner
`basicrum`, repository `basicrum-astro`, workflow `release.yml`, environment
`release`, explicitly allowing direct `npm publish`.

In a coordinated workflow change, remove the current empty-token skip and
secret reference, ensure npm is at least 11.5.1 and Node is at least 22.14.0,
and update README and AGENTS descriptions of token gating. The workflow
already has `id-token: write` and uses GitHub-hosted runners. Specifying only
Node major 22 does not establish the npm version floor. Revoke the bootstrap
token and remove its secret after a successful OIDC publish.
Source: [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/).

Without `NPM_TOKEN`, today's workflow deliberately skips npm and continues
to create a GitHub release. Removing the secret before changing that branch
would preserve the skip; configuring a trusted publisher alone is not enough.

## Consultation corrections and limits

- Fable withdrew its initial suggestion that non-consent should be described
  as consent managed elsewhere. Immediate loading without a consent decision
  is the intended contract.
- The current unpublished README and historical changelog were reclassified
  as release-preparation tasks rather than introduced P2 defects.
- An unresolved `NODE_AUTH_TOKEN` placeholder was not established as a bug.
  npm's official OIDC example uses `registry-url` without a token. Codex also
  checked a temporary matching npmrc with npm 11.13.0 and the variable unset:
  configuration parsing succeeded. This is not an OIDC authentication test.
- Publishing a tarball and generating provenance are documented features.
  No defect was established in using separate verification and publication
  jobs. See [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/).
- The existing `http-cache-semantics@4.2.0` advisory is in this repository's
  transitive Astro development dependencies. It was not introduced by the
  rename and is not shipped as a Basicrum runtime dependency. This does not
  assess consumers' own Astro installations or dismiss the advisory; track
  its assessment and dependency update separately.
- The example environment variables and vendor-description wording in
  THIRD-PARTY-NOTICES need not be renamed for this public API change. Dated
  review records should retain historical names.
